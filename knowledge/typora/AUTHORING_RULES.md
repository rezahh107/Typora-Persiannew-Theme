# Source-backed authoring rules — initial set

All points below were checked against official Typora documentation on **2026-10-23**. `DOCUMENTED` means the vendor states the behavior; it does **not** mean this repository observed it on every OS or build.

1. **Discoverability/install names (DOCUMENTED).** Each selectable theme is a CSS file directly within Typora's theme folder; use lowercase alphabetic filename pieces separated by hyphens. Install CSS/resources into that folder, restart Typora and choose the theme. Verify by actual menu selection. Sources: [About Themes](https://support.typora.io/About-Themes/), [Install Theme](https://theme.typora.io/doc/Install-Theme/). This repo adopts `<id>.css`; that is our repository convention.
2. **Scope selectors to actual content (DOCUMENTED).** Prefer ordinary HTML selectors such as `h1`, `p`, `table` scoped to `#write` when changing document appearance; otherwise global styles may also affect dialogs/controls. For base font size, use `html` and relative `rem` sizing so the app font-size preference works. Verify headings, table, menus and font-size setting in Typora. Source: [Write Custom Theme](https://theme.typora.io/doc/Write-Custom-Theme/).
3. **Code-fence lifecycle (DOCUMENTED), RTL stability (NOT_PROVEN).** Code fences are initially `pre.md-fences` (often `pre.md-fences.mock-cm`), then use CodeMirror with `.cm-s-inner` for fence syntax coloring. Source mode is distinct (`.cm-s-typora-default`). Style both pre-initialization and initialized states as needed; don't assume initial RTL rendering persists. Verify in real Typora immediately and after CodeMirror initialization with mixed-direction code and syntax highlighting; see `tests/fixtures/code-fences.md`. Sources: [Code Block Styles](https://support.typora.io/Code-Block-Styles/), [Write Custom Theme](https://theme.typora.io/doc/Write-Custom-Theme/).
4. **RTL is qualified (DOCUMENTED/EXPERIMENTAL).** The vendor describes RTL support as experimental and demonstrates `#write { direction: rtl; }`. This alone does not prove correct direction for code blocks, English spans, numbers or source mode. Avoid a blanket RTL rule for unrelated LTR themes. Verify cursor/order and readability with `tests/fixtures/rtl-ltr.md`. Source: [RTL](https://support.typora.io/RTL/).
5. **Local CSS overrides are a test variable (DOCUMENTED).** The cascade includes Typora base, selected theme CSS, `base.user.css`, then `<theme>.user.css`. Filename casing matters. Record or disable local overrides when producing visual evidence so other users can reproduce it. Source: [Add Custom CSS](https://support.typora.io/Add-Custom-CSS/).
6. **Resources and fonts (DOCUMENTED + legal boundary).** Typora permits relative theme assets/fonts and supports a `--monospace` variable for code styling. Existence of a font online does **not** establish redistribution rights. Keep only legally cleared assets in a theme and verify the actual resolved paths on install. Sources: [Custom Fonts](https://support.typora.io/Custom-Font/), [Write Custom Theme](https://theme.typora.io/doc/Write-Custom-Theme/).
7. **Print/export needs version-scoped evidence (DOCUMENTED, runtime NOT_PROVEN).** The authoring guide documents `@media print`; PDF export settings can choose a theme. The older [Export guide](https://support.typora.io/Export/) says Windows/Linux print only supports light themes, while the later [1.10 notes](https://support.typora.io/What's-New-1.10/) say dark PDF export on those platforms was enabled in 1.10. Treat this as a **version-sensitive change**, not a universal invariant. Test with an explicitly recorded Typora version, OS, and exported file before claiming support. Also see [Write Custom Theme](https://theme.typora.io/doc/Write-Custom-Theme/).

CSS structure or file-existence checks cannot establish selector compatibility, genuine Typora DOM timing, perceived layout, accessibility, print output or correct licensing. Maintain those distinct qualification states in the PR.
